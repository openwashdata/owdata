# Repo Orientation: owdata

> Generated by orient. Re-run to update.

## One-line purpose
owdata will be the index and documentation metapackage for the ~70 openwashdata R data packages: it ships a harvested catalog (packages, datasets, variables) as package data, provides `owd_search()` and `owd_install()`, and renders a searchable catalog on a pkgdown site refreshed by a weekly automated harvest.

## Primary language(s)
R (planned). No code exists yet — the repository currently contains only a README; the implementation plan is fully specified in GitHub issues #1–#12.

## Pipeline / workflow stages
The planned data flow, once implemented:

1. **Harvest** — `data-raw/harvest.R` lists all repos in the openwashdata GitHub org and fetches each package's `DESCRIPTION`, `data-raw/dictionary.csv`, `CITATION.cff`, and roxygen data docs (a local-clone backend exists for offline development and tests).
2. **Parse** — hardened parsers in `data-raw/harvest_helpers.R` normalize every known metadata pathology; unparseable packages land in a "problems" tibble rather than aborting the run.
3. **Classify** — `data-raw/tier_policy.R` assigns each package a tier (dev / candidate / catalogued) from its version number and Zenodo DOI, with a transitional "legacy" grandfather rule.
4. **Ship** — three tibbles (`owd_packages`, `owd_datasets`, `owd_variables`) are saved as package data, plus CSV/XLSX exports and `inst/extdata/catalog.json`.
5. **Serve** — exported functions (`owd_packages()`, `owd_search()`, `owd_install()`, …) query the shipped data; a pkgdown site renders searchable DT tables, including a ~2,500-row cross-org variable dictionary.
6. **Automate** — a weekly GitHub Actions workflow re-runs the harvest, gates the result with schema tests, and commits generated data straight to `main` (human code changes flow dev → PR → main).

## Core concepts
**Metapackage**: owdata contains no scientific data of its own; its "data" is a catalog *about* the org's ~70 data packages. Lives in `data/` as three tibbles once built.

**Version-tier inclusion policy**: catalog inclusion is gated by a mechanical version signal, not a manually curated list. dev (0.0.x) → candidate (0.1.0–<1.0.0; the 0.1.0 bump *is* the review request) → catalogued (≥1.0.0 plus Zenodo DOI). Defined in issue #2, implemented in `data-raw/tier_policy.R`.

**Harvest with two backends**: the same parsing logic runs against the GitHub API (`harvest_github()`) or local clones (`harvest_local()`), so the pipeline is testable offline. Issue #4.

**Failures are data, not errors**: per-repo tryCatch accumulates problems into a tibble; the run only fails CI if a shipped table would be empty or >10% of packages fail to parse. Issues #3 and #4.

**Bot commits to main**: generated data is committed directly to `main` by the weekly workflow, gated by schema tests — while human code changes go dev → PR → main. Issue #9.

## Common gotchas
- The repo looks empty but is not unplanned: all design decisions (schemas, column provenance, edge cases, even the malformed `Version: v1.0.0` in waterpointstatus) are already recorded in issues #1–#12. Implementing without reading the relevant issue will re-litigate settled decisions.
- `library(owdata)` must NOT attach or install the 70 data packages (issue #6) — only a startup message. This is easy to get wrong when mimicking the tidyverse metapackage pattern.
- The ~29 packages with a Zenodo DOI but version <1.0.0 are handled by a *temporary* grandfather rule (`legacy = TRUE`, issue #2); it is scheduled for deletion after the migration campaign (issue #10), so don't build anything permanent on it.
- Writing style in all package prose is an org rule: no em dashes, no emojis, blank line after headings (issue #12).
